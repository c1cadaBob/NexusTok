## 原生账号池唯一目标

项目已弃用 CPAMC/CLIProxyAPI/Sidecar 账号池路径。后续账号池功能只围绕 NexusTok 原生能力完善：

1. 账号池组、账号、认证文件、调度状态都由 NexusTok 主服务和主数据库维护。
2. 渠道账号池模式只应绑定原生 `AccountPoolGroup`，并通过本地 `PoolAccount` 完成选号和凭证注入。
3. Relay 热路径不得依赖 CPAMC/CLIProxyAPI 的外部分组、内部管理 key 或 sidecar 转发。
4. 既有 CPAMC/CLIProxyAPI 兼容代码属于待清理遗留路径，不能作为新增功能、校验逻辑或前端选项的依据。
5. 文档、测试和页面文案应统一表达“账号池 = 原生账号池”，避免继续引导用户配置外部 sidecar。

## sub2api 对照分析与原生实现方案评审

本节用于固定后续开发的设计边界：`/opt/project/sub2api-main` 只能作为账号池信息架构、账号/分组模型、调度策略和运行态管理的参考；NexusTok 最终实现必须沉淀为本项目主服务、主数据库和 Relay 热路径内的原生能力，不能把外部 sub2api 服务接入为依赖。

### sub2api 账号与分组能力拆解

基于当前源码复核，sub2api 的账号池核心模型是“全局账号资源 + 分组策略单元 + 多对多绑定”：

1. `accounts` 是全局账号表，保存账号名称、备注、平台、认证类型、凭据、扩展信息、代理、并发、优先级、计费倍率、状态、错误原因、最后使用时间、过期时间、是否可调度、限流恢复时间、过载恢复时间、临时不可调度时间和原因、会话窗口、额度维度等字段。
2. `groups` 是路由和策略单元，保存名称、描述、平台、状态、订阅类型、倍率、日/周/月额度、模型路由、支持模型范围、OpenAI Messages 调度配置、分组 RPM、fallback group 等策略字段。分组列表会聚合账号数量、活跃账号数量和限流账号数量。
3. `account_groups` 是账号和分组的多对多中间表，组合主键为 `account_id + group_id`，并保存组内 `priority` 和创建时间。一个账号可以属于多个分组，一个分组可以包含多个账号。
4. 账号管理请求的 `CreateAccountRequest`、`UpdateAccountRequest` 和批量编辑请求都支持 `group_ids`，即账号本身是全局资源，分组只是使用和调度视角。
5. 分组管理请求支持 `copy_accounts_from_group_ids`，创建分组时可从其它分组复制账号绑定，更新分组时可先清空当前绑定再复用其它分组的同一批账号。
6. 热路径选号以分组为入口，先尝试粘性会话，再查询可调度账号，过滤已排除账号、模型不匹配、分组不匹配、运行态阻塞、并发槽位、上游限制等条件，再按优先级、负载、LRU 或等待策略选择账号。
7. `Account.IsSchedulable()` 会排除非 active、`schedulable=false`、已过期、过载中、限流恢复时间未到、临时不可调度、API Key 或 Bedrock 额度耗尽的账号。
8. 前端信息架构把“账号管理”和“分组管理”拆成独立页面：账号列表默认展示全局账号，不按分组拆散；分组页负责分组策略、账号数量、复制其它分组账号和分组级配置。

这些设计说明：完整账号池不是“每个分组内孤立保存一份账号”，而是要让账号作为可复用资源，被多个策略分组引用，并在热路径中接受统一调度、状态、额度、并发和日志管理。

### NexusTok 当前原生实现对照

NexusTok 当前实现采用的是更保守的原生模型，重点是先保护已有 Relay 热路径稳定性：

1. `AccountPoolAuthFile` 表示全局凭证来源或导入记录，保存加密凭据原文、凭证摘要、来源格式、关联状态和来源信息。它更接近“凭证资源”，不是直接参与调度的热路径账号。
2. `PoolAccount` 表示某个账号池组内参与调度的运行时账号记录，保存 `pool_group_id`、`auth_file_id`、认证类型、凭据摘要、代理、模型/用户组限制、并发、RPM、每日请求、每日额度、冷却、不可用状态、成功/失败次数和最近检测时间。
3. `AccountPoolGroup` 是 NexusTok 的原生策略单元，保存平台、认证类型、来源、状态、调度策略、模型范围、渠道分组、模型映射、分组最大并发、分组 RPM、分组每日请求/额度、自动检测和运行前检测策略。
4. 当前多组复用通过 `PoolAccount.auth_file_id` 完成：一份 `AccountPoolAuthFile` 可以在多个账号组中派生多个 `PoolAccount` 调度实例。这样保持热路径仍以 `PoolAccount` 为选号、并发、额度、日志和状态更新对象。
5. 管理接口已提供 `POST /api/account-pool/groups/:id/accounts/attach`，支持从凭证列表批量选择加入目标账号组，也支持复用另一个账号组的同一批凭证。
6. 热路径 `SelectPoolAccount` 已支持分组启用校验、分组每日请求/额度限制、分组并发、分组 RPM、账号每日请求/额度限制、账号 RPM、排除本请求失败账号、冷却/不可用过滤、模型/用户组匹配、运行前检测、策略选号、账号并发预留和用量预占。
7. 失败处理、使用日志、状态日志、后台检测任务、自动检测、运行前预热、健康看板和安全导出都应继续围绕原生 `PoolAccount`、`AccountPoolAuthFile`、`AccountPoolGroup` 扩展。

当前模型和 sub2api 的根本差异是：sub2api 的账号实体本身是全局多对多资源；NexusTok 当前是“凭证全局、组内调度账号派生”。这个差异必须在 UI 和文档中讲清楚，避免把 `AccountPoolAuthFile.id`、`PoolAccount.id` 和账号组内序号混为一谈。

### 方案评审

方案 A：立即引入真正的 `pool_account_group_relations` 多对多关联表。

1. 优点：数据模型最接近 sub2api；一个账号实体天然可以加入多个账号组；跨组统一额度、并发、健康状态和审计语义更直接。
2. 缺点：这是大迁移，会影响模型、迁移、管理接口、热路径选号、并发预留、额度统计、失败处理、使用日志、状态日志、健康看板、删除语义、前端编号和历史数据兼容。任何处理不完整都可能影响现有 Relay 请求稳定性。
3. 适用时机：原生账号池主链路、检测、日志、跨组复用、渠道联动都稳定后，再以独立迁移阶段评估。

方案 B：维持当前“凭证全局 + 组内 `PoolAccount` 派生实例 + `AuthFileId` 关联”的模型。

1. 优点：改动可控，兼容已有调度、并发、额度、日志、检测和状态审计；可以先满足用户要求的“凭证列表全局展示、账号组批量选择凭证、一个凭证加入多个账号组”。
2. 缺点：同一凭证在多个账号组里会存在多个 `PoolAccount.id`，跨组统一并发/额度/健康状态需要额外策略；删除一个组内账号时必须避免误删全局凭证；UI 必须明确“凭证”和“调度账号”的区别。
3. 阶段推荐：当前阶段继续采用方案 B。只有当跨组统一额度、统一并发、统一健康状态成为明确需求且现有派生模型开始增加不可控复杂度时，再启动方案 A 的迁移评审。

### 需求分析

完整原生账号池至少要满足以下目标：

1. 账号/凭证全局管理：凭证可以导入、编辑、删除、脱敏展示、检测、刷新、追踪来源，并支持一个凭证加入多个账号组。
2. 账号组管理：账号组是策略单元，支持创建、编辑、删除、启停、批量添加凭证、复用其它账号组凭证、查看可用/异常/冷却/禁用数量。
3. 渠道联动：渠道账号池模式必须绑定原生 `AccountPoolGroup`，保存并使用 `credential_mode` 和 `account_pool_group_id`。
4. Relay 热路径：运行时按账号组筛选可用账号，执行并发、RPM、每日请求、每日额度、模型、用户组和运行前检测过滤，并按策略选号。
5. 失败恢复：账号失败时记录原因、排除当前请求、冷却或禁用、必要时自动切换其它账号；无可用账号时返回明确错误。
6. 可观测性：使用日志、状态日志、检测任务历史、健康看板、操作审计和安全导出都能追踪账号、凭证、账号组、渠道和请求。
7. 安全边界：凭证加密存储，接口响应和导出只返回脱敏摘要，日志不泄露 access token、refresh token、API key、Cookie、代理密钥或原始请求覆盖配置。
8. 不做事项：不把 CPAMC、CLIProxyAPI、Sidecar 或外部 sub2api 服务作为新增能力的依赖；不把外部分组或外部管理 key 作为原生账号池的运行前提。

### 影响范围分析

每次账号池代码改动前，必须按以下范围检查影响：

1. 数据模型和迁移：`model/account_pool.go`、迁移逻辑、旧数据兼容、SQLite/MySQL/PostgreSQL 兼容性。
2. 热路径：`service/account_pool_select.go`、`service/account_pool_error.go`、`middleware/distributor.go`、Relay channel key 注入、并发槽位释放、失败重试排除。
3. 管理接口：`controller/account_pool.go`、`router/api-router.go`、权限校验、输入校验、脱敏响应、批量操作边界。
4. 前端：`web/default/src/features/account-pool`、`web/default/src/features/channels`、路由、表单、列表密度、错误提示、i18n。
5. 日志和审计：使用日志、状态日志、检测任务、健康看板、导出格式、敏感字段过滤。
6. 运行环境：热更新开发容器、前端构建产物、Go embed 静态资源、MCP 浏览器验证。

### 风险评估

高风险点必须在设计和测试中显式处理：

1. 数据迁移不兼容三种数据库，导致 SQLite/MySQL/PostgreSQL 任一环境启动失败。
2. 热路径选号或释放槽位出错，导致所有 Relay 请求不可用、并发泄漏或账号长期被占用。
3. 多组复用后删除组内账号时误删全局凭证，或删除凭证时遗留可调度账号。
4. 同一凭证跨组派生多个 `PoolAccount` 后，额度、并发、健康状态和检测结果的语义不一致。
5. UI 同时展示凭证编号、调度账号编号和账号组编号，导致管理员误操作。
6. 外部导入凭据格式多样，检测、刷新、构造 channel key 时误判为失败或泄露原始凭据。
7. 缓存、前端构建 hash、Go embed 或热更新容器错位，导致页面可见但样式或交互异常。
8. MCP 验证只看页面是否打开，没有模拟真实操作、网络请求、响应体和控制台错误，导致功能表面可见但不可用。

### 2026-07-06：前端中文字体与样式异常方案评审

#### 需求分析

MCP 浏览器打开本地热更新页面和远端页面时，`/static/css/index.css`、主入口 JS 和账号池接口均返回 200，页面布局也已经挂载，但账号池中文界面在截图中出现大量方块字，用户感知会接近“样式丢失”或“页面错误”。这说明问题不只是静态资源 404，而是当前全局字体栈只声明 `Public Sans, sans-serif`，`Public Sans` 不包含中文字符；当运行环境没有系统 CJK 字体时，中文无法正常渲染。账号池后台需要在 Linux/容器/远程浏览器等字体较少的环境中稳定展示中文。

#### 影响范围分析

1. 前端全局样式：`web/default/src/styles/index.css` 的字体导入顺序，以及 `web/default/src/styles/theme.css` 中 `--font-sans`、`--font-inter`、`--font-manrope` 的字体栈。
2. 前端依赖：需要在 `web/default/package.json` 和 `bun.lock` 中增加可随构建产物一起发布的中文字体依赖，避免依赖用户本机是否安装中文字体。
3. 热更新构建：字体文件需要被 Rsbuild 正常打包到 `dist/static/font`，并继续由现有热更新发布流程原子替换到 `dist`。
4. 验证页面：重点验证 `/account-pool/groups`、`/account-pool/credentials`、`/account-pool/history` 和登录页，确认中文不再显示方块、CSS/JS 资源无 404、控制台无新增错误。

#### 风险评估

1. 中文字体包会增加前端构建体积，因此只作为中文 glyph 兜底引入，不改变主视觉字体和账号池页面结构。
2. 字体栈顺序需要保持英文界面仍优先使用 `Public Sans`，同时让中文字符能落到 `Noto Sans SC`、系统中文字体或通用 sans-serif。
3. 这次修复不触碰后端接口、账号池模型、Relay 热路径和热更新发布脚本，避免把字体显示问题扩大成运行路径改动。
4. 修改后必须通过 Bun typecheck/build 和 MCP 截图验证，确认不是仅在本机字体环境下可见。

#### 方案评审

采用轻量前端修复：引入 `@fontsource-variable/noto-sans-sc`，在全局样式中导入中文字体；在 Tailwind 主题字体变量里扩展跨平台字体栈，顺序为 `Public Sans`、`Noto Sans SC`、苹果/Windows/Linux 常见中文字体、系统 UI 字体和 `sans-serif`。该方案不新增页面逻辑、不改接口响应，不依赖外部 CDN，能让热更新和正式构建都携带必要字体文件。

### 2026-07-06：账号池状态审计精细检索方案评审

#### 需求分析

账号池状态日志已经能记录手动操作、后台检测、Relay 失败、额度冷却和凭据刷新等关键状态变化，但前端当前只暴露动作、来源和关键词搜索。管理员排查批量操作或单次请求时，还需要按时间范围缩小窗口、按 `request_id` 精确定位一批日志，并能从日志中的账号名快速筛到同一账号的历史变化。审计导出也应沿用同一组筛选条件，保证页面所见范围和导出快照一致。

#### 影响范围分析

1. 后端模型筛选：`PoolAccountStateLogFilter` 增加 `RequestId`，`applyPoolAccountStateLogFilter` 支持 `request_id = ?` 精确过滤，并让通用 `search` 覆盖 `request_id LIKE ?`。
2. 管理接口：`accountPoolStateLogFilterFromQuery` 读取 `request_id`，审计导出结果的 `filters` 返回该字段，便于导出文件自描述。
3. 前端历史记录页：状态日志视图增加 `Request ID`、开始时间、结束时间、清空筛选和账号筛选提示；日志表里的 request_id 和账号名可点击设置过滤条件。
4. 前端 API 类型和 i18n：状态日志列表、审计摘要和导出接口参数都补充 `request_id`；新增页面文案需要同步六语言。
5. 测试与验证：需要覆盖后端 request_id 精确过滤、search 命中 request_id、导出 filters 字段，以及 MCP 页面真实筛选和导出请求。

#### 风险评估

1. `request_id` 是审计定位字段，不包含凭证明文；但导出时仍只返回状态日志脱敏快照，不能扩展成凭据导出通道。
2. 时间范围使用秒级时间戳，前端 `datetime-local` 需要明确转换成本地时间对应的 Unix 秒，空值必须能清除。
3. 精确 request_id 过滤和通用 search 过滤同时存在时应取交集，避免快捷定位后又被旧搜索条件意外扩大范围。
4. 点击账号名只设置 `pool_account_id`，不改变日志写入或热路径状态；删除后的账号日志仍可按日志快照中的 ID 查询。
5. 本次改动只增强只读查询和前端筛选，不触碰 Relay 选号、并发预留、凭据注入和失败切换逻辑。

#### 方案评审

采用轻量增强现有状态日志接口的方案：不新增表、不修改状态日志写入结构、不引入新的审计索引模型；在现有筛选对象上新增 `request_id` 精确过滤，前端以紧凑两行筛选条承载时间和请求定位，并提供点击 request_id/账号名的快捷筛选。该方案可复用现有审计摘要和导出能力，改动边界清晰，符合“简单、清晰、明了”的页面要求。

## 总目标

账号池不是“能添加账号”的页面功能，而是一套可管理、可调度、可恢复、可观测、可扩展的凭证调度系统。

最终应达到的效果：

用户可以在账号池管理中维护多个账号和账号组，在渠道或任务配置中启用账号池模式并选择账号组。请求运行时，系统会自动从该账号组中筛选可用账号，根据调度策略分配账号，调用上游，记录使用日志。账号异常时系统能够标记状态、自动切换、冷却或返回明确错误。任务或请求结束后必须释放账号占用，并且页面能展示账号状态、可用数量、异常原因和使用记录。

## 必须打通的主链路

账号池功能是否真正可用，优先看下面这条链路是否闭环：

1. 管理员创建账号池分组。
2. 管理员向分组导入或创建账号。
3. 渠道配置选择“账号池模式”。
4. 渠道配置选择账号池分组。
5. 后端保存渠道的 `credential_mode` 和 `account_pool_group_id`。
6. Relay 请求选中该渠道。
7. Relay 根据 `account_pool_group_id` 查询组内账号。
8. 后端筛选启用、可调度、未冷却、未超并发、模型和用户组匹配的账号。
9. 后端按分组策略选择账号，并预留并发槽位。
10. 后端把账号凭证转换为上游可用的 channel key。
11. Relay 使用账号凭证完成上游调用。
12. 请求成功后记录账号使用量和成功计数。
13. 请求失败后记录失败原因，必要时冷却、排除该账号并切换下一个账号。
14. 请求结束后释放并发槽位。
15. 日志和页面可以追踪本次请求使用的账号池组和账号。

如果其中任一关键步骤缺失，账号池模式都还不能算完整实现。

## 第一阶段：主链路可运行

第一阶段目标是让账号池真正参与请求执行，而不是只停留在管理页面。

必须完成：

1. 账号表、账号组表、账号和组的关联关系可用。
2. 账号能新增、编辑、删除、启用、禁用。
3. 账号组能新增、编辑、删除。
4. 账号能加入指定账号组。
5. 渠道表单能启用账号池模式。
6. 渠道表单能选择账号池组，并展示该组可用状态。
7. 后端保存渠道配置时保留 `account_pool_group_id`。
8. 后端校验账号池组存在且启用。
9. Relay 请求能根据渠道绑定的账号池组选择组内账号。
10. Relay 能把选中账号的凭证用于上游调用。
11. 无可用账号时返回明确错误。
12. 成功和失败请求都能更新账号基础统计。

阶段验收：

1. 创建一个账号池组并导入至少一个可用账号。
2. 创建或编辑一个渠道，选择账号池模式和该账号池组。
3. 调用 `/v1/chat/completions` 或对应 Relay 接口。
4. 日志里能看到使用的账号池组和账号。
5. 禁用该账号后再次调用，应返回账号池无可用账号或切换到其他可用账号。

## 第二阶段：稳定性与恢复能力

第二阶段目标是让账号池面对真实错误时稳定运行。

必须完成：

1. 账号状态管理：启用、禁用、不可用、冷却中、登录失效、额度耗尽等。
2. 手动检测单个账号可用性。
3. 批量检测账号可用性。
4. 失败次数统计。
5. 失败后自动记录错误原因。
6. 达到失败阈值后自动冷却或禁用。
7. 请求重试时排除已失败账号。
8. 账号冷却结束后自动恢复可调度。
9. 账号级最大并发控制。
10. 请求异常结束也必须释放账号占用。
11. 使用日志可以按账号、账号组、渠道或请求查询。
12. 前端展示账号组健康状态：总数、可用数、禁用数、冷却数。

阶段验收：

1. 人为制造一个账号失败，请求应记录失败原因。
2. 同一请求重试时不应继续选择已排除账号。
3. 设置最大并发为 1 后，并发请求不能同时占用同一账号。
4. 账号冷却期内不会被选择，冷却结束后可再次参与调度。

第三阶段目标是完善生产级能力。

建议完成：

3. 频率限制：账号级、账号组级、任务级频率限制。
4. 定时检测账号可用性。
5. 自动刷新 OAuth 凭证。
6. 自动恢复冷却账号。
7. 账号池统计看板。
8. 批量导入、批量导出、批量状态修改。
9. 多用户权限边界。
10. 敏感凭证加密、脱敏和审计。

阶段验收：

1. 不同调度策略在测试中能产生预期选号结果。
2. 额度不足的账号不会被继续选择。
3. 定时刷新失败会设置下次重试时间并记录原因。

## 前端页面目标

账号池管理页至少需要：

1. 顶层子目录固定为：概览、账号凭证、分组、日志历史。
2. 账号凭证页作为默认入口，默认列出所有已导入凭证，不按分组拆散展示。
3. 账号凭证页展示账号身份、所属文件、提供方、分配分组、调度规则和状态；账号身份应位于主信息位置，所属导入文件作为次级信息展示，避免把文件记录误认为账号本身。
4. 分组页单独管理账号池分组、组内账号、调度策略和分组级限制。
5. 新增和编辑账号组。
6. 新增和编辑账号。

9. 批量操作。

11. 账号检测。
12. 使用日志。
13. 账号组健康状态：总数、可用数、禁用数、冷却数。
14. 一个账号凭证应被视为可复用资源；分组只是调度/使用视角，后续如要做到一份凭证物化到多个账号池组，需要补齐后端多组关联或派生账号模型。

编号语义：

1. 账号凭证页中的文件编号是 `AccountPoolAuthFile.id`，代表导入凭证文件/凭证记录，用于编辑、删除和追踪来源。
2. 分组或调度日志中的账号编号是 `PoolAccount.id`，代表某个账号在账号池分组内参与调度的运行时账号记录。
3. 当前实现中一份凭证通常会生成一个关联的 `PoolAccount`；未来支持一份凭证分配到多个组时，同一凭证可能派生出多个 `PoolAccount`，因此 UI 应明确区分“所属文件”和“调度账号”，默认不要在列表里同时展示两个未命名编号。

1. 分组页的右侧主标题应显示当前分组名，而不是泛泛显示“分组”。
2. 分组自动检测、运行前检测、策略和模型范围属于分组摘要信息，应并入分组头部或详情区域，不应单独占据一整行。
3. 未选择账号时不展示批量操作按钮；只有选中账号后再显示启用、禁用、清除冷却、导出和删除等批量操作。
4. 组内账号列表应以账号身份作为主信息，所属文件作为次级信息；`PoolAccount.id` 属于调度账号技术编号，默认可放入悬停提示或详情，不应和文件名混在一起展示。

6. 用量列默认展示今日请求、成功次数和失败次数；并发、RPM、额度、权重、优先级等限制细节可放入悬停提示或账号详情中。

7. 当前账号池组的可用账号数量。
8. 当前账号池组的异常账号数量。
9. 保存时正确传递 `credential_mode` 和 `account_pool_group_id`。

## 安全和权限目标

账号池保存的是敏感凭证，必须遵守以下约束：

1. 密码、Token、Cookie、OAuth 凭证必须加密存储。
2. 接口响应不能返回完整敏感凭证。
3. 前端只能展示脱敏摘要。
4. 日志中不能泄露账号密钥。
5. 编辑凭证时使用重新填写机制。
6. 删除账号时清理关联信息。
7. 后端调用时统一解密。
8. 管理接口必须有管理员权限。
9. 后续多用户场景中，任务只能使用有权限的账号组。
10. 操作日志需要记录操作者。

## 异常处理目标

必须对以下场景给出明确行为：

1. 账号组不存在。
2. 账号组未启用。
3. 账号组为空。
4. 账号组没有可用账号。
5. 所有账号都在使用中。
6. 所有账号都在冷却中。
7. 账号登录失效。
8. 账号请求失败。
9. 账号额度耗尽。
10. 账号被禁用。
11. 请求执行中账号突然不可用。

错误信息应该能帮助管理员定位问题，不能统一吞成“任务失败”。

### 2026-07-06：兼容 Sub2api access-token-only Codex 账号

已确认 Sub2api 可测试成功、但 NexusTok 原生账号池检测失败的根因：

1. Sub2api 导出的 Codex 账号是 `credential_mode=access_token_only`，通常只有当前可用的 `access_token`，没有可刷新用的 `refresh_token`。
2. Sub2api 的测试流程直接使用当前 `access_token` 调模型，因此只要 token 仍在有效期内就能成功。
3. NexusTok 原生账号池之前把 `official_oauth` 账号统一当作可刷新 OAuth 账号处理，检测和后台自动刷新会先调用 provider refresh；对 access-token-only 账号来说，这一步必然失败。
4. Sub2api 凭据里的 `expired`/`expires_at` 可能是 Unix 数字，而原生 Codex OAuth 结构原先按字符串解析，也会导致凭据被误判为无效。

已完成的修复目标：

1. Codex OAuth 凭据解析改为宽松读取，兼容 `expired`/`expires_at` 为数字或字符串，并支持 `account_id`、`accountId`、`chatgpt_account_id` 等字段名。
2. Codex 账号构造 relay channel key 时，会把外部导入凭据规范化为最小 OAuth JSON，只保留 relay 热路径需要的字段，避免额外元数据影响请求。
3. 对明确标记 `credential_mode=access_token_only` 或 `refreshable=false` 的官方 OAuth 账号，人工检测和后台自动刷新会跳过 refresh，改为验证凭据能否构造可调用 key。
4. 保持原生 OAuth 登录账号默认可刷新，避免影响已有带 `refresh_token` 的账号。
5. 新增单元测试覆盖 access-token-only 账号检测成功、自动刷新跳过、Codex key 规范化和缺少 `refresh_token` 时的明确错误。

后续注意事项：

1. access-token-only 账号无法长期自动续期，过期后需要重新导入或补齐真正可刷新的 OAuth 凭据。
2. 已经被旧逻辑标记为不可用的账号，需要重新执行单账号检测或批量检测，检测成功后会清除旧错误和冷却状态。
3. 账号池组元信息应与组内账号保持一致，例如 Codex 官方 OAuth 账号组不应配置成无关平台或 API key 类型，否则后续筛选和展示可能继续产生歧义。

7. 已补齐前端六种语言翻译，并增加 model/controller 测试覆盖审计摘要、批量操作聚合、分组筛选、导出格式和敏感字段不外泄。

### 2026-07-06：无空闲账号等待策略方案评审

本节用于本轮开发前固定设计边界：目标是补齐 P3 中“无空闲账号时可配置等待或失败”的第一步，不引入全局任务队列，也不改变旧账号池组的默认调度行为。

需求分析：

1. 当账号池组或组内账号因为并发槽位已满而暂时没有空闲账号时，管理员应能配置“立即失败”或“短暂等待空闲账号”。
2. 默认策略必须保持立即失败，确保已有渠道、已有账号池组和现有 Relay 延迟行为不变。
3. 等待只处理并发占用这类短暂资源不足；每日额度耗尽、RPM 超限、账号禁用、冷却、运行前检测缺失、分组为空等非短暂问题仍应立即返回明确错误。
4. 等待必须有最大超时时间，并设置安全上限，避免 Relay 请求被无限挂起。
5. 前端分组弹窗应能配置该策略，并在分组摘要中展示当前处理方式，保持“简单、清晰、明了”。

影响范围分析：

1. 数据模型：`AccountPoolGroup` 需要新增“无空闲账号处理策略”和“等待超时时间”字段；迁移继续依赖 GORM `AutoMigrate`，保持 SQLite/MySQL/PostgreSQL 兼容。
2. 热路径：`service/account_pool_select.go` 需要把选号逻辑拆成单次尝试和等待包装层，只在账号/分组并发满时重试，且必须正确恢复当前请求的排除账号集合。
3. 管理接口：创建、编辑、列表、详情和渠道账号池组选项需要返回新字段。
4. 前端：`web/default/src/features/account-pool` 需要补充类型、表单字段、摘要文案和 i18n。
5. 测试：需要覆盖默认立即失败、等待后成功、等待超时和非并发错误不等待。

风险评估：

1. 如果等待逻辑复用同一个请求上下文但不恢复临时排除账号，忙账号会在释放后仍被排除，导致等待策略失效。
2. 如果等待范围过宽，额度耗尽、冷却或检测缺失这类无法通过短等待恢复的问题会拖慢请求并掩盖真实错误。
3. 如果超时时间不设上限，管理员误配置可能导致大量 Relay 请求长时间占用连接。
4. 如果默认值处理错误，旧分组可能从“立即失败”变成“等待”，影响现有核心业务延迟。
5. 如果前端摘要不清晰，管理员可能误以为这是完整任务队列；页面文案必须表达为“无空闲账号处理”，而不是“全局队列”。

方案评审：

1. 方案 A：引入完整持久化任务队列。优点是可做全局排队和任务级并发；缺点是会影响 Relay 同步响应模型、任务系统、超时、取消和日志，当前阶段风险过高。
2. 方案 B：在账号池组上新增默认关闭的短等待策略。优点是改动边界清晰，能解决最常见的并发满短暂等待场景；缺点是仍不是完整任务队列，不能处理长时间排队、任务级公平性或跨用户隔离。
3. 当前采用方案 B。后续如要实现真正任务级并发/频率控制，应在任务模型和 Relay 请求上下文中设计独立的任务标识、队列容量、取消语义和审计日志。

已完成的实现目标：

1. 账号池分组新增 `no_available_action` 和 `no_available_wait_seconds`，默认 `fail` 保持旧分组立即失败；`wait` 仅在分组/账号并发槽位已满时短暂等待。
2. Relay 热路径拆分为单次选号和等待包装层；等待重试前会恢复当前请求进入本次尝试前的排除账号集合，避免并发满账号释放后仍被当前请求排除。
3. 等待策略只处理 `ErrPoolAccountGroupConcurrencyExceeded` 和 `ErrPoolAccountConcurrencyExceeded`；RPM、每日额度、冷却、禁用、检测缺失和分组为空继续立即返回原错误。
4. 等待秒数由模型层规范化，默认 5 秒，最大 30 秒，防止误配置导致 Relay 请求长期占用连接。
5. 创建/编辑账号组接口、账号组列表响应和渠道账号池组选项都返回新字段；前端账号组弹窗支持配置，并在账号组摘要中展示“立即失败”或“最多等待 N 秒空闲账号”。
6. 已补充服务层、控制器、前端类型、六语言 i18n 和 MCP 页面验证。

仍未完成的重点目标：

1. 真正任务级频率限制和任务级并发限制。
2. 完整持久化队列、队列容量、取消语义和多用户公平调度。
3. 多用户权限边界，以及后续任务只能使用有权限账号组的隔离策略。

### 2026-07-07：账号池异步任务提交级限流方案评审

本节用于本轮开发前固定设计边界：目标是补齐 P3 中“任务级并发限制、任务级频率限制”的第一步。这里的“任务级”先限定为异步任务提交请求，例如视频生成、音乐生成等 `RelayTask` 提交流程；它保护账号池分组在某一类 `platform + action` 任务提交时的瞬时并发和每分钟提交频率。它不改变同步 Chat/Responses Relay，也不把账号占用延长到上游异步任务真正完成。

需求分析：

1. 账号池已经具备账号级和分组级并发/RPM，但这些限制不区分任务类型；同一账号池组内不同异步任务动作可能互相挤占。
2. 管理员需要能在账号池组上配置异步任务提交最大并发和每分钟最大提交数；默认必须为 0，表示不限制，确保旧分组、旧渠道和同步请求行为不变。
3. 限流维度采用 `account_pool_group_id + platform + action`，让同一账号池组内不同任务动作独立计数；用户组、用户 ID、渠道 ID 暂不进入 key，避免把分组保护能力稀释成单用户限流。
4. 并发满时应支持“立即失败”或“短暂等待槽位”；等待仍只用于可由请求结束释放的并发槽位，频率限制达到上限时立即返回 429，避免请求挂到下一个分钟窗口。
5. 任务级限流应在异步任务参数校验通过、计费预扣费之前执行，避免已知会被账号池任务策略拒绝的请求提前扣费。
6. 任务提交成功或失败后必须释放任务级并发槽位；异常返回、上游失败和本地校验失败路径都不能泄漏槽位。

影响范围分析：

1. 数据模型：`AccountPoolGroup` 需要新增任务提交最大并发、任务提交 RPM、任务并发满处理策略和等待秒数字段；迁移继续依赖 GORM `AutoMigrate`，保持 SQLite/MySQL/PostgreSQL 兼容。
2. 热路径：新增服务层任务限流器，并在 `RelayTaskSubmit` 里调用；同步 Relay 的 `SelectPoolAccount` 不变，账号级/分组级限流不受影响。
3. 管理接口：账号池组创建、更新、详情、列表和渠道账号池组选项需要透出新字段。
4. 前端：账号组弹窗需要增加一组紧凑的“异步任务”控制项，并在账号组摘要中显示当前任务级策略。
5. 测试：需要覆盖默认关闭、并发预留/释放、并发满立即失败、并发满等待后成功、RPM 超限，以及 API 字段读写。

风险评估：

1. 如果任务级限流放在计费预扣费之后，用户可能因为任务策略拒绝而发生不必要的扣费/退款路径。
2. 如果并发槽位释放不覆盖所有返回路径，后续任务会长期误判为并发满。
3. 如果限流 key 过粗，只按分组限流，会把不同任务动作混在一起；如果 key 过细，分组保护又可能失效。本阶段选择 `group + platform + action` 作为清晰且可解释的折中。
4. 如果等待策略也用于 RPM，可能让请求在分钟窗口边界附近长时间挂起，并和现有 Relay 超时、客户端取消语义冲突；因此 RPM 只立即失败。
5. 如果前端把该能力描述成“完整任务队列”，管理员会误以为异步任务会排队到上游完成；页面文案必须明确为“提交级”控制。

方案评审：

1. 方案 A：实现真正持久化任务队列，任务从提交到上游完成前都持有账号池槽位。优点是语义最完整；缺点是会影响 `Task` 状态机、轮询、超时、退款、取消、重启恢复和多用户公平性，当前阶段风险过高。
2. 方案 B：在账号池组上增加默认关闭的异步任务提交级并发/RPM 控制。优点是改动边界清晰，能防止某类任务短时间打满账号池提交能力；缺点是它不等于完整队列，也不约束上游任务运行到完成的全过程。
3. 当前采用方案 B。后续如果要做到“任务真正结束后释放账号占用”，需要单独设计任务状态表和账号池占用之间的持久关系、服务重启恢复、超时释放、失败退款和管理员可见审计。

已完成的实现目标：

1. 账号池分组新增 `task_max_concurrency`、`task_rate_limit_rpm`、`task_limit_action` 和 `task_limit_wait_seconds`，默认并发/RPM 为 `0`，表示不限制；旧账号池组升级后不会改变原有异步任务提交行为。
2. 新增 `service.ReserveAccountPoolTaskLimit` 和 `ReleaseAccountPoolTaskLimit`，限流键固定为 `account_pool_group_id + platform + action`；Redis 可用时使用 Redis 计数，Redis 不可用时回退进程内计数。
3. `RelayTaskSubmit` 在异步任务参数校验完成后、模型计费和预扣费之前执行任务提交限流；本地限流错误会返回 429，并且不会进入任务重试分发。
4. 并发满时支持 `fail` 或 `wait`；`wait` 只等待当前 HTTP 请求内可释放的提交槽位，默认 5 秒、最大 30 秒。RPM 超限始终立即失败，不等待下一个分钟窗口。
5. 账号池组创建、更新、详情、列表和渠道账号池组选项都返回任务提交限流字段；默认前端账号组弹窗新增任务提交并发、任务提交 RPM、任务并发动作和任务等待秒数字段，并在分组摘要展示当前提交级策略。
6. 已补充 controller 字段读写测试、service 限流测试、前端类型和六语言 i18n；MCP 已验证 `POST /api/account-pool/groups`、`PUT /api/account-pool/groups/:id`、`GET /api/account-pool/groups` 的字段读写与规范化，并在 default 前端 `/account-pool/groups` 验证摘要和编辑弹窗控件正常渲染。

仍未完成的重点目标：

1. 持久化任务队列、队列容量、取消语义、多用户公平调度，以及任务真正完成后才释放账号池占用。
2. 任务提交级限流的管理审计和更细权限边界；后续 Authz 上线后，账号池分组任务限流配置应归入账号池敏感策略写权限。
3. 在真实视频/音乐等异步上游 channel 中补充端到端用例，确认不同 `platform + action` 任务不会互相挤占。

### 2026-07-06：热更新页面无样式问题修复方案评审

本节记录当前热更新容器中“页面出现错误、样式没有了”的诊断和修复目标，避免后续继续在同一问题上反复排查。

需求分析：

1. 当前热更新开发容器需要稳定服务默认前端页面，页面刷新时不能因为前端构建产物切换而丢失 CSS。
2. 普通本地 `bun run build`、前端 watch 构建和 Go 后端 embed 编译不能互相覆盖出不一致的 `dist`。
3. 热更新模式下前端产物使用稳定文件名时，浏览器不能对 `/static/*`、`/assets/*` 做一周强缓存。
4. 静态资源缺失返回 404 时也不能被强缓存，否则一次短暂构建窗口期的错误会在浏览器侧持续存在。

影响范围分析：

1. Docker 热更新编排需要调整 `frontend-watch` 的启动方式，使其先构建到临时目录，再发布到 Go embed 使用的 `dist`。
2. 后端热重载脚本需要只根据“前端发布完成标记”触发重编译，避免直接扫描正在变化的 `dist` 文件。
3. 默认前端 Rsbuild 和经典前端 Vite 需要支持通过环境变量指定临时输出目录。
4. 缓存中间件需要识别热更新模式，热更新下静态资源改为 `no-cache`。
5. Web SPA 回退逻辑需要保证缺失静态资源 404 不被强缓存。

风险评估：

1. 如果仍直接 watch 写入 `dist`，Go embed 可能在构建中间态读取到旧 HTML 配新 CSS，或新 HTML 配旧 CSS。
2. 如果手动生产构建覆盖 `dist` 后热更新容器不自愈，页面会再次进入 hash/no-hash 资源混用状态。
3. 如果热更新下继续强缓存稳定文件名的 JS/CSS，浏览器会把旧资源和新 HTML 组合，造成页面无样式或运行时错误。
4. 如果后端脚本扫描整个 `dist`，发布过程中的文件增删会触发多次重编译，并增加嵌入半成品的概率。

方案评审：

1. 方案 A：继续使用 `rsbuild build --watch` 直接写入 `dist`。实现简单，但无法解决普通构建覆盖和后端 embed 半成品的问题。
2. 方案 B：前端构建到临时目录，成功后带发布锁和标记发布到 `dist`；后端只观察发布标记。实现稍复杂，但能把构建中间态从后端 embed 路径隔离出去。
3. 当前采用方案 B，并补充热更新静态资源 `no-cache`，同时对缺失静态资源 404 覆盖为 `no-cache`。
